## What changed and why

Custos is a private, agentic RAG assistant that answers questions from a business's own document corpus, where the stated differentiator is the security controls rather than the RAG quality: `THREAT_MODEL.md` names eight threats (T1-T8) and states that a control without a passing adversarial eval does not count as shipped. User-visible behavior: a person asks a question in the React UI, receives an SSE-delivered answer with resolved citations after complete-response redaction, and can ask the assistant to draft an email or file a ticket, both of which are always simulated and always require an explicit confirmation click before anything is recorded as "executed." Switching a demo access tier (`general`/`hr`/`finance`) changes what the assistant can retrieve and answer from. System-level behavior not visible in the UI: every retrieved chunk and every tool output is scanned for injection patterns and wrapped as untrusted data before it reaches the model; every complete answer is scanned for SSNs, personal emails, and personal phone numbers and masked before any answer text is released; every side-effectful tool call is intercepted before execution, not after; and the vector-store backend, the agent-loop runtime, and the LLM provider are each independently swappable via environment variable, with the non-default option in each pair proven (not merely assumed) to satisfy the same eval suite as the default.

## Architecture and data flow

A synchronous request (`POST /api/chat`) and a streaming request (`POST /api/chat/stream`) both follow the same shape; the streaming path is the one that actually creates confirmable pending actions (see the choices table), so it is traced here.

1. **Entry** (`src/custos/api.py :: chat_stream`): the request body (`query`, `user_permissions`, `history`, `session_id`) is untrusted client input in its entirety; the endpoint's own module docstring calls this out for `user_permissions` specifically. `history` is trimmed to the last `MAX_HISTORY_MESSAGES = 20` entries and filtered to well-formed `{role, content}` dicts (`src/custos/api.py :: _trim_history`).
2. **Readiness gate**: `_require_ready()` checks the module-level `_index_ready` flag before doing any work; if the boot-time index check never succeeded, the request is rejected before touching the vector store or the LLM.
3. **Rate limiting** (`src/custos/rate_limiter.py :: RateLimiter.check_request`): query length, then monthly cap, then daily cap, then per-IP sliding window, then per-session quota, in that order; the first violated limit returns a user-facing message and the request stops here. This is a request-scoped check, evaluated before any retrieval or generation cost is incurred.
4. **Retrieval** (`src/custos/retriever.py :: CustosRetriever.retrieve`, invoked from `src/custos/api.py :: _retrieve_and_scan`): the query is embedded locally, then the configured `VectorStore.query()` is called with `user_permissions` as a server-side filter. This is the source of truth for "what this caller is allowed to see"; there is no second, independent access check anywhere downstream. The returned chunks are immediately passed to `InjectionDetector.scan()`, which sanitizes matched spans in the prompt copy only, never the underlying document.
5. **Prompt assembly** (`src/custos/llm.py :: build_prompt`): system instructions and the (sanitized) retrieved chunks are structurally separated; chunks are wrapped as labeled untrusted data.
6. **Agent loop** (`src/custos/agent_loop.py :: AgentLoop.run_streaming`): calls the provider's streaming transport, but emits only text-free progress checkpoints and takes answer text from the SDK's authoritative final message. It parses `tool_use` blocks structurally, gates side effects, executes read-only tools inline, and wraps tool results as untrusted data. Bounded by `max_steps` (5) and `timeout_seconds` (30).
7. **Output resolution** (`src/custos/llm.py :: resolve_response`): strips citations, replaces dashes, and redacts PII from the complete answer. Only then does either runtime emit the answer as a client-visible `text_delta`; no corrective `text_replace` is the security boundary. Citation IDs are resolved only against real retrieved chunks.
8. **Confirmation, out of band** (`POST /api/chat/confirm`, `src/custos/api.py :: confirm_action`): a later, separate request, keyed by the `action_id` emitted in step 6 and bound to the `session_id` that created it. This is the one place a side effect actually "happens" (still simulated at the tool level, see the choices table).

**Sources of truth:** the vector store is the source of truth for content and retrieval permissions. `PendingActionStore` is an in-memory, task-local source for confirmations. `data/counters.json` persists budget counters across a process restart only when the filesystem remains. The ECS task definition mounts no application-data volume, so task replacement loses that file; no state described here is shared across tasks.

**Transaction boundaries:** there are none in the database sense; there is no database. The closest analogue is `PendingActionStore.consume()`, a single dict `pop()` used specifically to make confirmation one-shot (a second confirm request for the same `action_id` gets 404, not a double execution). Vector-store writes (`ingest`) are not transactional with reads; `/api/ingest` recreates the entire collection, and a query arriving mid-recreation would see a partial or empty index, a case not specifically tested (see Verification performed).

## Security and privacy

- **Identity and authorization:** There is none, by design and stated as such. No FastAPI route has an auth dependency except `/api/admin/status` (bearer-token check against `CUSTOS_ADMIN_TOKEN`, fails closed if unset). `/api/chat`, `/api/chat/stream`, and `/api/ingest` accept a client-declared `user_permissions` value with no verification against any identity system. `THREAT_MODEL.md` names this as an explicit, scoped-out Phase 4 item, not a discovered gap.
- **Tenant isolation:** Not applicable in the multi-customer sense; this is a single-corpus, permission-tagged-document model (`general`/`hr`/`finance`/`owner` in the demo), not a multi-tenant system with tenant-scoped data. A real multi-tenant deployment would need to extend the permission model, not just wire in auth.
- **Input/output trust boundaries:** Retrieved chunks and tool outputs are untrusted data, structurally separated from system instructions. The previous version of this rationale claimed streaming output was PII-masked before leaving the process; that was false when a value crossed emitted-chunk boundaries, and a second reviewer demonstrated the leak. Both runtimes now withhold answer text until the complete response has passed through `resolve_response()`, backed by prefix-property regression tests.
- **Sensitive data:** The shipped corpus (`corpus/generate.py`, `demo/corpus/`) is entirely synthetic, using reserved ranges that cannot collide with a real person (`example.com`/`example.org` emails, `555-0100`-`555-0199` phones, `900`-`999` SSN area codes). Tier 1 PII is masked unconditionally in answers and in logs (`PIIFormatter` on every log handler). Tier 2 PII (DOB, salary, address, names) is not masked, a stated and reasoned deferral, not an oversight (ADR-005).
- **Secrets and external services:** `.env` is git-ignored; `.gitleaks.toml` scans everything except `corpus/.*` (allowlisted specifically because that corpus's PII is synthetic by construction) and runs on every push/PR via `.github/workflows/secrets.yml`. In the AWS customer deployment, the Anthropic API key (if used) lives only in Secrets Manager, set out-of-band via CLI, never in Terraform state; in Bedrock mode, no long-lived model credential exists anywhere, the ECS task authenticates via its own task role.
- **Known abuse cases:** Prompt injection (direct and indirect, T1/T2), data exfiltration via answer or tool argument (T3), PII exposure (T4), unauthorized retrieval (T5), tool abuse (T6), and denial/cost abuse via runaway loops or oversized input (T7) are all named in `THREAT_MODEL.md` with a corresponding eval. Supply-chain/secret leakage (T8) is defended structurally (git-ignore, pinned deps, the gitleaks scan) but graded DEFENDED-manual in the threat model itself, not ENFORCED, an honest self-grading rather than an overclaim.

## Performance, scale, and cost

- **Expected workload:** Not defined anywhere in the repo as a target (no stated requests/second, concurrent-user, or corpus-size goal). What exists is a 63-chunk, 9-document demo corpus, and the rate limiter's defaults (150 requests/day, 4000/month, 8/minute/IP, 25/session) read as sized for a low-traffic public demo, not a load target derived from measurement.
- **Potential limiting resources:** Live LLM API latency dominates wall-clock time per the agent-runtime benchmark below (multiple seconds per call, versus low-single-digit-millisecond local vector queries). The embedding model download on first run (`BGE-small`, ~130MB) is a one-time cost, cached afterward. The streaming bridge (`_advance_in_thread`) consumes one worker thread per concurrent stream for its duration; not load-tested beyond the two-concurrent-request case in `tests/test_stream_concurrency.py`.
- **Measured evidence:**
  - Vector-store backend comparison (ADR-001, `docs/benchmarks/vector-backends.md`): 35 fixed queries against the 63-chunk demo corpus, both backends as local Docker containers on identical hardware. Qdrant p50 3.70ms / p95 4.79ms; pgvector p50 0.78ms / p95 1.03ms; `recall@5 = 1.000` between them. The ADR itself states this corpus size is too small for either backend's index to be under real load, and that pgvector's lower latency here is more likely a transport-protocol artifact than a finding about the two ANN implementations; a capacity decision at hundreds of thousands to millions of vectors would need a re-run at that scale, which has not happened.
  - Agent-runtime comparison (ADR-006, `docs/benchmarks/agent-runtimes.md`): 15 fixed queries x 3 repetitions x 2 runtimes = 90 live calls against a real `ANTHROPIC_API_KEY`. native p50 2593ms / p95 5867ms; langgraph p50 2292ms / p95 4544ms; mean `input_tokens` identical to one decimal place across 45 calls per runtime (1481.2). The ADR itself states the benchmark ran all of one runtime's calls before the other's, sequentially, so it cannot distinguish a real framework latency effect from ordinary API-side drift, and explicitly claims no latency winner despite the raw numbers favoring langgraph.
  - Reproduced independently this pass: `python -m custos.ingest` against the demo corpus completed in a few seconds locally (63 chunks, 2 upsert batches); `python -m evals.harness` with Qdrant up completed in well under a minute.
- **Budget:** The only defined budget is cost-based, not latency- or throughput-based: `src/custos/rate_limiter.py` derives an estimated cost per query from fixed assumed token counts (`EST_INPUT_TOKENS = 4050`, `EST_OUTPUT_TOKENS = 600`) and Sonnet's published per-token price, tracked against the persisted monthly cap, with `scripts/budget-alert.sh` pushing a notification at 50% and 80% of that cap. This is an estimate, not metered from Anthropic's actual billing API, stated as such in this document's companion `docs/ENGINEERING_OVERVIEW.md`.

No claim of scalability beyond the demo corpus's 63 chunks and the benchmark's own stated request volumes is made here; both the vector-store and agent-runtime ADRs name a scale re-test as a prerequisite for any larger claim, and neither has been re-run at scale as of this document.

## Rollout, rollback, and operations

- **Deploy/migration order:**
  - Live demo (`docs/DEPLOY_RUNBOOK.md`): DNS record created and resolving *before* the VM is provisioned (Let's Encrypt validates over HTTP against the real hostname and will hit rate limits on repeated failure otherwise); the API's DNS record must be DNS-only in Cloudflare, not proxied, or the rate limiter's IP-based logic is silently defeated; Docker stack up, then Caddy installed and started only after DNS resolves; UI built separately with the production `VITE_API_URL` and uploaded to Cloudflare Pages.
  - AWS customer module (`deploy/terraform/`, `deploy/PREREQUISITES.md`): account id and an assumable IAM role must exist before any `terraform plan`; the `enable_egress`/`llm_provider` combination must be chosen jointly, since two of the four combinations are blocked at plan time by named `precondition` guards; for pgvector, `scripts/migrate_pgvector.py` must run before the app can serve traffic against that backend.
- **Healthy signals:** `/api/health` (readiness, not liveness, per the invariants table); `/api/admin/status` (token-gated diagnostic exposing `index_ready`, `chunks`, `expected_chunks`, `qdrant_connected`); the ALB target group in the Terraform module health-checks `/api/health` with a 3-consecutive-success/3-consecutive-failure threshold at a 10s interval. No metrics, tracing, or Prometheus stack is wired up; `ARCHITECTURE.md` now marks that accurately as not built.
- **Rollback or forward recovery:** `deploy/EVIDENCE.md` documents one full `terraform destroy` cycle after the one recorded apply, confirmed clean (`0 to add, 0 to change, 34 to destroy`, NAT gateway and load balancer confirmed gone afterward). For the live demo, `docker compose -f docker-compose.prod.yml up -d --build` is the stated update path (`docs/DEPLOY_RUNBOOK.md`'s "Updating" section); no documented rollback procedure exists for a bad deploy on that path beyond `git checkout` to a prior commit and rebuilding, which is not written down anywhere as a runbook step.
- **Runbook/docs updated:** `docs/DEPLOY_RUNBOOK.md` (live demo), `deploy/README.md`, `deploy/PREREQUISITES.md`, `deploy/EVIDENCE.md` (AWS module). `docs/ENGINEERING_OVERVIEW.md` (written this week, separate document, whole-repo architecture and drift audit) is a relevant companion to this file and overlaps in places by design; this document is decision-rationale-and-verification focused, that one is architecture-and-behavior focused.

## Known compromises and uncertainty

| Item | User/operational consequence | Why accepted now | Owner | Revisit trigger |
|---|---|---|---|---|
| No real authentication on `/api/chat` or `/api/chat/stream`; permissions are client-declared | Anyone who can reach the API can claim any access tier and retrieve anything | Accepted only for the synthetic portfolio demo | Not specified (no ownership metadata in repo) | Before any deployment holding real customer documents |
| `/api/ingest` is unauthenticated and recreates the collection | Anyone with network access can trigger destructive reindexing and create an availability/integrity event | Accepted only for the synthetic portfolio demo; authentication was explicitly out of scope for this pass | Not specified | Before any deployment holding real customer documents |
| Plain HTTP remains available through explicit Terraform opt-in | Credentials, queries, permissions, and documents can be observed or modified in transit if an operator deliberately enables it | Needed only for an isolated synthetic-data demo; TLS is now the default and missing/half-configured TLS fails mocked plan tests | Not specified | Before any deployment holding real customer documents |
| Tier 2 PII (DOB, salary, address, personal names) is not masked | A cleared user's answer could still surface these types if they appear in retrieved content; access control (T5) is the only defense for them today | ADR-005: naive regex on these types would corrupt legitimate operational answers (a price looks like a salary); shipping a fragile detector was judged worse than an honest deferral | Not specified | NER/disambiguation approach built and evaluated (named in ADR-005 as the eventual right tool, not attempted yet) |
| `/api/chat` (sync) cannot produce a confirmable pending action at all; only `/api/chat/stream` can | A caller of the sync endpoint that reaches a side-effectful tool_use gets a "requires confirmation" message with no way to actually confirm it | ADR-006 states this is a pre-existing asymmetry, deliberately replicated rather than fixed while doing an unrelated runtime comparison, to keep that comparison's scope honest | Not specified | Either endpoint parity is decided as a requirement, or the sync endpoint is documented as read-only-safe-tools-only |
| Pending actions and all rate/budget controls are task-local; ECS has no persistent application-data mount | Confirmations can 404 on another task; the monthly cap is multiplied by task count; task replacement loses file-backed counters | Adequate for a single-task demo, and Terraform now refuses `desired_count > 1` | Not specified | Multi-instance deployment becomes a requirement |
| Fully air-gapped AWS deployment (`enable_egress=false`) does not work for either LLM provider | A customer whose policy requires no internet route from any workload cannot be deployed today, regardless of which model provider they choose | The ECS task's Qdrant sidecar is pulled from Docker Hub at apply time; the module does not yet mirror it into the customer's ECR | Not specified | `deploy/PREREQUISITES.md` states this should be raised before scoping any engagement with an air-gap requirement, i.e., the trigger is a real customer asking, not a scheduled fix |
| Vector-store and agent-runtime latency/recall benchmarks were both run at demo-corpus scale (63 chunks) only | Neither backend/runtime choice has been validated at a scale anywhere near what a real customer corpus might be | Both ADRs (001, 006) state this limitation themselves and describe it as a re-run prerequisite for any larger claim, not a hidden gap | Not specified | A real customer corpus large enough to make the choice matter |
