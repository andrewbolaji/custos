# Custos Security Questionnaire

Answered against this repository's actual code and configuration, not from
memory or marketing copy. Every row cites a repository path, a test name,
or a workflow name in the Evidence column. Where a row has no such path,
it is marked **NOT IMPLEMENTED** — plainly, not softened. A control that is
claimed and absent is worse than one that is absent and disclosed; that
rule governs every answer below, and Section 10 governs the document as a
whole.

Two deployment paths exist and differ materially: **standard**
(`enable_egress = true`, ECS Fargate reaches the public internet through a
NAT gateway) and **air-gapped** (`enable_egress = false`, no route out).
Where an answer depends on which one you're running, both are given
explicitly rather than blurred into one. As of this document, **the
air-gapped path does not deploy at all** — it is blocked at
`terraform plan` time for every model provider. This is stated up front
because it recurs through several sections below and the reason is the
same each time: the ECS task also runs a Qdrant vector-store sidecar
pulled from Docker Hub (`deploy/terraform/ecs.tf`), which an air-gapped
subnet cannot reach, and this module does not yet mirror that image into
ECR. See `deploy/terraform/guard.tf` (`egress_provider_guard`) and
`deploy/PREREQUISITES.md`'s "Network and egress" section.

## 1. Data handling and residency

| Question | Answer | Evidence |
|---|---|---|
| Where does our document corpus live? | Self-hosted vector store you control: Qdrant (default) or pgvector, selected by `CUSTOS_VECTOR_BACKEND`. In the standard AWS deployment, Qdrant runs as a sidecar container inside your own ECS task, not a shared or vendor-hosted service. | `docs/decisions/001-vector-store.md`; `deploy/terraform/ecs.tf` (Qdrant sidecar in the same task definition) |
| Is our raw document text sent to a third party? | Only the specific retrieved chunks relevant to a given query are sent to the model provider (Anthropic, or Amazon Bedrock in `bedrock` mode) as part of that one generation call. The full corpus is never uploaded to the model provider; storage and retrieval stay on infrastructure you operate. | `src/custos/llm.py::build_prompt` (assembles only the retrieved chunks); `ARCHITECTURE.md` |
| Are embeddings computed locally or by a third party? | Locally. `LocalEmbedder` runs BGE-small (`BAAI/bge-small-en-v1.5`) in-process; no embedding API call leaves the deployment. | `src/custos/embedder.py`; README.md "Privacy by default" |
| Can we choose a specific AWS region for data residency? | Yes, `region` is a required Terraform variable with no default forcing a choice; all resources (Qdrant volume, logs, secrets) are created in that one region. | `deploy/terraform/variables.tf` (`region`); `deploy/PREREQUISITES.md` "Region and data residency" |
| Is PII redacted from data at rest (the index)? | No — by design, not by omission. Redaction happens at answer time and in logs, not at ingest, so that authorized users (e.g., a permission tier scoped to see real values) are not shown pre-corrupted data. Document-level access control (`retriever.py`) is the primary control on who reaches PII-bearing chunks at all. | `docs/decisions/005-pii-redaction.md` ("Where redaction happens" — explicitly rejects ingest-time redaction, with reasoning) |
| Is our data used to train Custos or any underlying model? | No. Anthropic's API does not train on customer prompts/completions by default (see Section 5, Subprocessors, for the specific provider commitment this depends on and where that commitment is documented). Nothing in this codebase persists query/answer pairs for a training pipeline. | `docs/SECURITY_QUESTIONNAIRE.md` §9 (Subprocessors); no training-data collection code exists in `src/custos/` |
| How is the demo/seed corpus's PII handled? | It is entirely synthetic, generated with reserved, non-issuable ranges (RFC 2606 email domains, ITU-T 555-01xx phone numbers) so no value can match a real person. This is a fixture property, not a production data-handling claim. | `corpus/generate.py` (`ReservedPII`); `.gitleaks.toml` comment explaining the same for `demo/corpus/` |

## 2. Access control and authentication

| Question | Answer | Evidence |
|---|---|---|
| Is document access enforced per user/role? | Yes, at retrieval — a permission filter is applied inside the vector store query itself (Qdrant payload filter or Postgres `WHERE` clause, matching `CUSTOS_VECTOR_BACKEND`), not in the prompt or in application logic after the fact. A restricted document is never fetched into the model's context for an unauthorized caller. | `src/custos/retriever.py`; `src/custos/vector_store.py::_build_filter`; `src/custos/vector_store_pgvector.py::query`; THREAT_MODEL.md T5 |
| Is this proven, or just asserted? | Proven with a hard-gate eval and unit tests exercised against both supported backends: an unauthorized caller retrieves **zero** restricted chunks, not "fewer." | `evals/suites/retrieval.py` (4 access-control cases, run in CI on both backends — `.github/workflows/ci.yml`'s `backend` matrix); `tests/test_retriever.py::TestAccessControlHardGate` |
| What happens to a document with no permission tag, or a user with no granted permissions? | Fail-closed on both sides. An untagged document is retrievable by no one; a user with an empty permission list retrieves nothing. This falls out of the filter construction itself (`MatchAny` against an empty list / SQL array-overlap against an empty array), not a special-cased check that could be forgotten. | `src/custos/vector_store.py::_build_filter` docstring; `tests/test_retriever.py::TestFailClosedPermissions` (4 cases) |
| Is there per-user authentication (login) today? | **No — this is the most important row in this section.** `user_permissions` is supplied by the client in the request body. In this build, nothing authenticates that the caller is who they claim; a malicious client could claim `["hr","finance"]`. This is documented in the code and the threat model, not discovered externally. Real auth (JWT/IdP-backed identity mapped to a permission list) is a planned integration, not a redesign — the access-control mechanism already takes a permission list as input; only the source of that list changes. | `src/custos/api.py` (`ChatRequest` docstring: "DEMO SIMPLIFICATION..."); THREAT_MODEL.md "Client-supplied trust boundaries" |
| Is the admin/ingest surface protected? | `/api/admin/status` requires a bearer token (`CUSTOS_ADMIN_TOKEN`), compared with `secrets.compare_digest` (constant-time) and returns 404 rather than 401/403 on failure or missing token, so the route's existence isn't disclosed to an unauthenticated prober. `/api/ingest` is **unauthenticated** in this build — documented as a demo simplification, real deployments should place it behind the same identity boundary as admin actions generally. | `src/custos/api.py::admin_status`, `::ingest` (docstring: "DEMO SIMPLIFICATION: unauthenticated") |
| Is there session hijacking / CSRF risk on the confirmation flow (approving a side-effectful action)? | Pending actions use an unguessable `uuid4` id, are bound to the `session_id` that created them, expire after 5 minutes, and are single-use (consumed on confirm/reject). A session mismatch on confirm returns 403. | `src/custos/pending_actions.py` (module docstring states all four invariants); `tests/test_pending_actions.py`; `tests/test_confirm.py` |

## 3. Encryption in transit and at rest

| Question | Answer | Evidence |
|---|---|---|
| Is traffic to the app encrypted by default? | Depends on deployment path, stated precisely: the standalone VM path (`docker-compose.prod.yml`) terminates TLS via Caddy with auto-provisioned Let's Encrypt certificates. The **AWS Terraform module's ALB ships with only an HTTP (port 80) listener by default** — the HTTPS listener is present in the file but commented out until you supply a custom domain and ACM certificate ARN. Until then, traffic to the AWS deployment's public endpoint is plain HTTP. | `Caddyfile`; `deploy/terraform/alb.tf` (HTTPS listener commented, lines ~46 onward); `deploy/PREREQUISITES.md` "Custom domain and TLS" |
| Is ALB-to-container traffic inside the VPC encrypted? | No — it is plain HTTP, but confined to a security-group-restricted path (ALB → ECS tasks only, by security group id, not CIDR) inside a private subnet with no public IP on the task. This is a common, accepted pattern for intra-VPC traffic; it is not TLS. | `deploy/terraform/alb.tf` (target group `protocol = "HTTP"`); `deploy/terraform/security.tf` (`aws_security_group.ecs_tasks` scoped to the ALB SG only) |
| Is the model provider call (app → Anthropic/Bedrock) encrypted? | Yes — both `api.anthropic.com` (HTTPS, standard) and Amazon Bedrock (accessed over a private VPC interface endpoint using TLS) are encrypted in transit. In `bedrock` mode with `enable_egress = false`... — see the air-gapped caveat at the top of this document; that specific combination does not currently deploy for an unrelated reason (the Qdrant sidecar), not because of this row. | `deploy/terraform/network.tf` (`aws_vpc_endpoint.bedrock_runtime`) |
| Is data at rest encrypted? | Relies on each AWS service's own default encryption, not a customer-managed KMS key configured by this module — no `kms` or `encrypt` resource exists in `deploy/terraform/`. Concretely: Secrets Manager encrypts secret values by default; ECR encrypts stored images by default (SSE-S3); CloudWatch Logs encrypts stored log data by default; Fargate encrypts task ephemeral storage by default. None of these are opt-outable by this module, but none are upgraded to a customer-managed key either — that would be a legitimate ask for a higher-assurance deployment and is not built today. | `deploy/terraform/secrets.tf`, `ecr.tf`, `logs.tf` (no `kms_key_id` argument set on any of them, confirmed by inspection) |
| Are the Qdrant/pgvector data volumes encrypted? | In the AWS deployment, Qdrant's storage is the ECS task's ephemeral storage (AWS-default-encrypted, see above) — it is **not** persistent across task replacement, which is a deliberate design point (see `deploy/README.md`'s "Health check is the readiness gate" section: every fresh task reindexes on boot). Locally / in the standalone VM deployment, Qdrant's data is a Docker named volume on the host's own disk, whose encryption depends on the host's disk encryption, outside this project's control. | `deploy/terraform/ecs.tf` (no EFS/EBS volume mounted for Qdrant, ephemeral container storage only); `docker-compose.yml`/`docker-compose.prod.yml` (`qdrant_data` named volume) |

## 5. AI and model-specific risk

| Question | Answer | Evidence |
|---|---|---|
| Prompt injection — direct (user tries to override instructions) | System prompt structurally separates trusted instructions from untrusted content; retrieved chunks and tool outputs are wrapped and labeled as data, never merged into the instruction channel. | THREAT_MODEL.md T1; `evals/suites/injection.py` (12 cases, run in CI — `evals.harness.SUITE_MODULES`) |
| Prompt injection — indirect (a retrieved document contains an instruction) | Two independent layers. **Detection:** a heuristic scanner matches known override patterns (role impersonation, "ignore instructions," admin claims, hidden HTML/`[INST]` blocks) and replaces matched spans with a neutral placeholder before the prompt is built — the source document itself is never modified. **Prevention:** even if detection misses a novel injection and the model emits a tool call, side-effectful tools still cannot execute without confirmation (Section 6/T6) — this holds structurally, independent of whether detection caught anything. | `src/custos/injection_detector.py`; THREAT_MODEL.md T2; `evals/suites/action_gating.py::injection_cannot_cause_execution` (deliberately bypasses the detector to prove the gate alone holds — RED-TEAMED against a live model) |
| Is detection alone the security boundary? | No, and this is stated as a matter of principle, not hedging: detection is heuristic and honestly documented as such — "novel injections will evade it." The tool-execution gate (Section 6) is the actual boundary; detection is a UX/defense-in-depth improvement on top of it, not a substitute for it. | `src/custos/injection_detector.py` module docstring |
| Does the model train on our conversation data? | Depends on the subprocessor — see Section 9. Anthropic's standard API terms do not use customer API data to train models. This is a provider commitment, not something enforced by this codebase; verify current terms directly with your model provider before relying on it contractually. | Section 9 (Subprocessors); no training-data export exists in this codebase to make the point moot regardless |
| Output handling — PII in answers | Tier 1 PII (SSN, personal email, personal phone) is masked unconditionally in every answer, regardless of the requesting user's permission tier, inside `resolve_response()` — the single function every output path (sync and streaming) funnels through. Company-public contacts survive via an explicit allowlist. | `src/custos/pii.py`; `src/custos/llm.py::resolve_response`; THREAT_MODEL.md T4; `evals/suites/pii.py` (22 cases) |
| Output handling — what PII is NOT masked | Date of birth, salary figures, street addresses, and personal names — stated plainly, with the specific reason: a detector precise enough to catch these also catches legitimate data of the same shape (product prices, office addresses), and that false-positive rate degrades retrieval more than it protects. Document-level access control is the primary control for this category today. | `docs/decisions/005-pii-redaction.md` "Tier 2" table (per-type reasoning); THREAT_MODEL.md "Explicitly out of scope" |
| Can the model take an action (send an email, file a ticket) on its own? | No. Every side-effectful tool call, regardless of what triggered it (a direct user request or an injected instruction), produces a pending confirmation and executes nothing until a human approves it. The gate is on execution, not on the model's request. | `src/custos/agent_loop.py` (module docstring: "SECURITY INVARIANTS"); THREAT_MODEL.md T6; `evals/suites/action_gating.py` (7 structural + 1 RED-TEAMED case); `tests/test_agent_loop.py` |
| Is the agent loop bounded (can't be made to run forever / spend unbounded money)? | Yes — `max_steps` (default 5) and `timeout_seconds` (default 30) bound every agent run. | `src/custos/agent_loop.py` (`DEFAULT_MAX_STEPS`, `DEFAULT_TIMEOUT_SECONDS`); THREAT_MODEL.md T7; `evals/suites/action_gating.py::max_steps_enforced` |
| Model provider subprocessors | See Section 9. |

## 10. Known limitations

Every control absent from this system is listed here, with the mitigation
or the reason it is out of scope. A filled-in limitations section is the
signal that this questionnaire was written against the code, not copied
from a template.

| Limitation | Mitigation / reason out of scope | Evidence |
|---|---|---|
| **No per-authenticated-user identity.** `user_permissions` is client-supplied on every request. | Documented as a demo simplification from day one, not discovered post-hoc.
