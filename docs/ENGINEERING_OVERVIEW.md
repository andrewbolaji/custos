# Custos engineering overview

Custos is a private, agentic RAG assistant that answers questions from a business's own document corpus, where the security controls are the differentiator, not a bolt-on. A user asks a question, the app retrieves permission-filtered chunks, an LLM answers with citations, and an agent loop can call tools, some of which are simulated and gated behind explicit human confirmation before anything executes. This document lets a reviewer with read access to the repo, and no other context, spend their time on judgment rather than archaeology. Every behavioral claim cites the file and symbol it comes from: `path/to/file.py :: symbol_name` for Python, `path/to/file.tf :: resource_name` for Terraform. Where a claim could not be pinned to a symbol, or where I went looking for a discrepancy and did not find one, that is stated directly rather than implied either way. Several docs here (`CLAUDE.md`, `docs/DECISIONS.md`'s ADR-006 entry, `docs/SECURITY.md`) state numbers the code and a live run of the test/eval suites contradict; those go in Testing and Unverified below, not silently corrected in place.

## What you can and cannot run

Python 3.12 exactly (`CLAUDE.md`, deps pin `<3.13`; a wheel-availability constraint on `torch`, not a style preference), Node 20, and `make`. `make install` builds a `.venv` and runs `npm install` in `ui/`; no credentials needed. `make check` (ruff, `mypy --strict`, `pytest`, `vitest`) runs fully mocked, no Supabase-style backing service, no API key, confirmed by direct run below. `make evals` (deterministic adversarial suite) needs a running Qdrant container (`make up`) and a built index (`make index`) but no API key; without Qdrant it still exits 0 and prints `NOT PROVEN`, not a failure, see Testing. Nothing behind `--llm` (`make evals-full`), nothing calling `ANTHROPIC_API_KEY`-gated `/api/chat` or `/api/chat/stream` for real, and nothing in `deploy/terraform/` against an actual AWS account is exercisable without credentials a reviewer will not have: an Anthropic API key or AWS Bedrock access, an AWS account matching `deploy/terraform/variables.tf :: expected_account_id`, and (for the live demo site specifically) `CUSTOS_ADMIN_TOKEN` for `/api/admin/status` and `scripts/budget-alert.sh`. `docker compose up -d qdrant` plus `python -m custos.ingest` is enough to get the full deterministic eval suite running locally with zero external credentials; I did this to verify the counts below.

## 1. How to read this repo

Start with `CLAUDE.md`, then `THREAT_MODEL.md` (T1-T8, the assets and trust boundaries this whole codebase defends) and `ARCHITECTURE.md`'s diagram. Then `src/custos/interfaces.py`, the pluggable-component contracts (`Embedder`, `VectorStore`, `Retriever`, `LLM`, `Redactor`, `Guardrail`, `Tool`) that the rest of the package implements against. Then `src/custos/api.py :: app`, the single FastAPI application and every route. Then `src/custos/agent_loop.py :: AgentLoop`, the state machine that is the actual enforcement point for tool-use gating. `docs/decisions/*.md` are ADRs; read them in order, they are the most reliable source in the repo because two of them (`001-vector-store.md`, `006-agent-runtime.md`) carry dated "Measured" addenda appended after implementation, not rewritten in place, so you can see what was predicted versus what was later verified by running it.

## 3. The comparison thesis: two of almost everything

**Vector store** (ADR-001, `docs/decisions/001-vector-store.md`). `QdrantVectorStore` (`src/custos/vector_store.py`) is the default; `PgVectorStore` (`src/custos/vector_store_pgvector.py`) is a documented alternate for deployments that already run Postgres, selected by `CUSTOS_VECTOR_BACKEND`. Both implement `VectorStore` from `src/custos/interfaces.py`. The access-control filter (T5 in the threat model) is enforced inside the query itself on both: a Qdrant `MatchAny` payload filter in `QdrantVectorStore.query()`, or a Postgres `WHERE permissions && %s` array-overlap clause in `PgVectorStore.query()`, evaluated in the same statement as the ANN `ORDER BY`, never a Python post-filter. Both fail closed on an empty permission set through the primitive itself (`MatchAny` cannot match an empty payload list; array-overlap against an empty array is always false in Postgres), not through a special-cased sentinel. ADR-001's Measured section reports the full deterministic eval suite passing identically on both backends and a latency/recall benchmark (`docs/benchmarks/vector-backends.md`) showing `recall@5 = 1.000` between them at the 63-chunk demo corpus's scale, with the explicit caveat that this scale is too small to say anything about a production-sized corpus.

**Agent runtime** (ADR-006, `docs/decisions/006-agent-runtime.md`). `AgentLoop` (`src/custos/agent_loop.py`) is the hand-rolled default; `LangGraphAgentLoop` (`src/custos/agent_loop_langgraph.py`, `langgraph.graph.StateGraph`) is a second implementation, selected by `CUSTOS_AGENT_RUNTIME`, sharing the same `run()`/`run_streaming()` contract via `src/custos/agent_runtime.py :: build_agent_loop`. This ADR's headline finding is a warning, not a recommendation: `tests/test_langgraph_prebuilt_defeats_gate.py` demonstrates that LangGraph's own documented quickstart path (`ToolNode` + `tools_condition`, or `create_react_agent`) executes a side-effectful tool inside a single `graph.invoke()` call with no confirmation step at all, pinned to `langgraph==1.2.9`. `LangGraphAgentLoop` does not use that path; it hand-writes `_node_gate_and_execute` to replicate the native loop's gating logic node-for-node. Both runtimes pass the full 61-case deterministic suite and the full 73-case suite including LLM-dependent cases (ADR-006's own numbers, reproduced independently below in Testing). Measured token overhead between the two is zero (identical mean `input_tokens` across 45 live calls each, per `docs/benchmarks/agent-runtimes.md`); no latency winner is claimed, because the benchmark script runs all of one runtime's calls before the other's, sequentially, which the ADR itself flags as unable to distinguish a real framework effect from ordinary API-side drift.

**LLM provider** (ADR-003). `ClaudeLLM` calls `api.anthropic.com` directly; `BedrockLLM` calls Amazon Bedrock via `anthropic.AnthropicBedrock(aws_region=...)`, selected by `CUSTOS_LLM_PROVIDER`. In Bedrock mode, `BedrockLLM` passes no explicit credential kwarg at all, `src/custos/llm.py`'s own comment states the SDK signs requests with whatever boto3's default credential chain resolves, the ECS task role in production, so there is no long-lived model credential to leak in that mode specifically. `tests/test_llm_bedrock.py :: TestBedrockLLMNoCredentials` asserts this by checking the exact kwargs passed to the SDK constructor, not just reading the comment. The Bedrock model default is `us.anthropic.claude-sonnet-4-6`, the region-pinned inference profile, deliberately never the `global.` profile, because the global profile can route to any commercial region for capacity reasons, which would defeat the data-residency property the Bedrock path exists to provide.

## 4. The RAG pipeline

Ingest starts from `corpus/generate.py`, a 781-line deterministic generator (`SEED` default `42`, `REFERENCE_DATE` default `2026-07-17`, both env-overridable) that produces a synthetic corpus for a fictional company, "Meridian Home Services." All synthetic PII uses ranges that can never collide with a real person: emails at `example.com`/`example.org` (RFC 2606 reserved), phones `555-0100` through `555-0199` (ITU-T E.123 fictional range), SSNs in the `900`-`999` area-code range (never issued by SSA). `src/custos/chunker.py :: chunk_document` is a structural Markdown chunker (ADR-004), not fixed-size splitting: it splits on heading boundaries first, then on paragraph boundaries only for any section exceeding `MAX_CHUNK_CHARS = 1500`. Every produced chunk's `char_start`/`char_end` offsets are verified against the source text before the function returns (`text[chunk.char_start:chunk.char_end] == chunk.text`, raising `ValueError` on mismatch), which is the actual mechanism that makes a citation resolve to a real span rather than an approximate one. `src/custos/embedder.py :: LocalEmbedder` embeds locally with `BAAI/bge-small-en-v1.5` (384 dimensions), lazily loaded on first use; no document content or embedding call leaves the deployment in the default configuration.

At query time, `src/custos/retriever.py :: CustosRetriever.retrieve(query, user_permissions, k=5)` embeds the query and calls the configured `VectorStore.query()` with the caller's permissions as a server-side filter. `src/custos/llm.py :: build_prompt` structurally separates instructions from untrusted retrieved data. `resolve_response()` strips citations, normalizes punctuation, and redacts PII from the complete answer. The provider transport is still consumed incrementally, but both agent runtimes emit only text-free progress checkpoints until resolution completes; only the fully resolved answer becomes client-visible text.

The two read-only tools available to the agent, `src/custos/tools/search_documents.py :: SearchDocumentsTool` and `src/custos/tools/summarize_section.py :: SummarizeSectionTool`, both route through the exact same `Retriever.retrieve()` call as the primary query path, not a separate lookup, so a tool-triggered search inherits the same permission filter as a direct question.

## 5. The security controls, threat by threat

`THREAT_MODEL.md` names eight threats, T1 through T8, and grades each control against a four-level taxonomy stated in the file itself: RED-TEAMED (a live LLM adversary attempted the attack and the control held), ENFORCED (the control operates in the real request path, exercised with real data), STRUCTURED (defensive structure verified present, not behaviorally exercised), DEFENDED-manual (verified by inspection, no CI automation yet). That taxonomy is the honest part worth reading closely: the repo distinguishes what is actually proven under adversarial pressure from what is merely correctly assembled, and says so instead of collapsing both into "passing."

**T1/T2, prompt injection.** Two independent layers, and the file is explicit that they are complementary rather than redundant. Detection is heuristic: `src/custos/injection_detector.py :: InjectionDetector` runs nine compiled regex patterns (role impersonation, instruction-override phrasing, admin-claim social engineering, hidden HTML comments, prompt-template markers, and others) against every retrieved chunk, replacing only the matched span with `[injected instruction removed]`, never the whole chunk, and never the source document. The module's own docstring states its limit directly: "detection is heuristic. Novel injections will evade it." Prevention is structural and does not depend on detection working: `evals/suites/action_gating.py`'s `injection_cannot_cause_execution` case deliberately bypasses the detector, builds a poisoned chunk directly, and proves that even when the model obeys the injected instruction and emits a `send_email` tool-use block, the hard gate in `AgentLoop` still blocks execution before it happens. This is the project's stated thesis: the gate is on execution, not on the model's request, and it holds even when model alignment fails.

**T4, PII exposure.** `src/custos/pii.py :: PIIRedactor` masks SSNs, personal emails, and personal phones unconditionally. Company-public contacts survive explicit allowlists; Tier 2 DOB/salary/address/name detection remains deliberately deferred in ADR-005. An earlier version of this overview relied on complete-answer `resolve_response()` while overlooking that streaming chunks had already reached the browser. A second reviewer reproduced a complete SSN across concatenated deltas. Both runtimes now buffer answer text until complete-response redaction, and regression tests exercise every split position and every accumulated client-visible prefix. Log output is independently redacted by `PIIFormatter`.

**T5, unauthorized access.** Covered in section 4; the eval (`access_control:qdrant` in the harness output, four hard-gate cases) proves `unauthorized_chunks = 0` against the real retriever, not a mocked one.

**T6/T7, tool abuse and runaway loops.** Covered in section 3's runtime discussion and section 7 below. `AgentLoop`'s loop bound (`max_steps`, `timeout_seconds`) is the T7 control, exercised by `evals/suites/action_gating.py`'s `max_steps_enforced` case against the real loop, not a stub.

**T8, supply chain and secrets.** Structural only: `.env` is git-ignored, `.gitleaks.toml` scans everything except `corpus/.*` (allowlisted because the demo corpus's PII is synthetic by construction, see section 4), and `.github/workflows/secrets.yml` runs `gitleaks/gitleaks-action@v2` on every push and PR to `main`. `THREAT_MODEL.md` grades this DEFENDED-manual, not ENFORCED, and says CI automation beyond the secret scan is still pending; that grading matches what actually exists.

**What the repo explicitly does not claim**, stated in `THREAT_MODEL.md`'s own "Explicitly out of scope" section: network/infrastructure hardening beyond the application, formal model-weight security, nation-state adversaries, Tier 2 PII, and real authentication. The last of those is not a minor footnote; it shapes section 6 below.

## 6. Auth and its actual enforcement mode

State the current behavior, not the intended one, the same standard `THREAT_MODEL.md` sets for itself. There is no authentication middleware and no auth dependency on any FastAPI route in `src/custos/api.py`. `/api/chat`, `/api/chat/stream`, and `/api/ingest` have no server-side identity check at all. `ChatRequest.user_permissions` (default `["general"]`) is taken directly from the client-supplied request body and used as the retrieval permission filter described in sections 4 and 5; the module's own docstring states this outright, "A client could claim `["hr", "finance", "owner"]` and access everything. This is documented, not hidden." `/api/ingest` recreates the vector collection and reindexes the entire corpus with no credential required at all, also called out in the same docstring as a demo simplification. The one credential-gated route is `/api/admin/status`: `src/custos/api.py :: admin_status` checks the request's bearer token against `CUSTOS_ADMIN_TOKEN` with `secrets.compare_digest` (timing-safe), and fails closed, if the env var is unset (empty string default), the check can never pass and the route always returns 404, deliberately not 401 or 403, so an unauthenticated caller cannot tell the route exists at all.

`/api/chat/confirm`, where a pending side-effectful action is actually approved or rejected, is gated by possession of an unguessable `action_id` (a `uuid4`) plus a `session_id` match against the session that created the pending action, and a five-minute TTL. That is replay protection scoped to one session, not identity authentication; two people sharing a `session_id` could confirm each other's actions.

None of this is presented as a finished security posture. `deploy/PREREQUISITES.md` asks a customer directly whether they have an existing identity provider (Okta, Azure AD, Google Workspace) the deployment should integrate with, and states plainly that without an answer, "we deploy with the simplest access model available (single shared credential or a flat role list) and it has to be reworked once your actual identity provider and role structure are known." `THREAT_MODEL.md` lists real authentication as a named, explicit, out-of-scope item for the current phase, not an omission discovered by reading the code.

## 7. Tool use and the confirmation gate

Four tools are registered per request in `src/custos/api.py :: _build_registry(user_permissions)`: two read-only (`SearchDocumentsTool`, `SummarizeSectionTool`) and two side-effectful and permanently simulated (`SendEmailTool`, `FileTicketTool`, `src/custos/tools/`). Every side-effectful tool's `run()` always returns a result whose text ends in `(simulated)` and whose `simulated` field is `True`; there is no code path where either tool sends a real email or files a real ticket. In `AgentLoop.run()` and `run_streaming()` (and identically in `LangGraphAgentLoop._node_gate_and_execute`), any `tool_use` block naming a side-effectful tool is never executed inline. Only `run_streaming()` creates a real `PendingAction` (`src/custos/pending_actions.py :: PendingActionStore`, an in-memory dict keyed by `uuid4`, default TTL `DEFAULT_TTL_SECONDS = 300`); the synchronous `run()` path used by `/api/chat` emits the same confirmation event but never creates a `PendingAction` at all, so `/api/chat` (non-streaming) cannot produce a confirmable action, only `/api/chat/stream` can. ADR-006 names this directly as a pre-existing product asymmetry it chose to replicate exactly rather than quietly fix while doing an unrelated runtime comparison.

The confirm/reject lifecycle (`POST /api/chat/confirm`, `src/custos/api.py :: confirm_action`) never had to change for the LangGraph work, because both runtimes only ever emit a confirmation event or create a `PendingAction`; neither self-executes. That endpoint checks, in order: unknown or already-consumed action id (404), expired TTL (410), session mismatch (403), then either records a rejection or actually invokes `tool.run()` (still simulated at the tool level) and marks the action executed. `tests/test_confirm.py` and `tests/test_pending_actions.py` exercise this lifecycle directly, not just the happy path.

## 8. Client architecture

React 19 and Vite 6 (`ui/package.json`) talk to the API over `VITE_API_URL`. The client sends the demo access group as `user_permissions`, which the UI discloses through `DemoBanner`. `/api/chat/stream` remains SSE, but answer text is no longer token-by-token: the sync provider stream is advanced through `asyncio.to_thread`, emitting internal `stream_progress` checkpoints for disconnect/concurrency scheduling, then one fully resolved/redacted answer delta. A controlled five-chunk stream with 20 ms between chunks measured first client-visible text at 22.3 ms before the fix and 111.9 ms after it; in production the added delay is the rest of model generation. `tests/test_stream_concurrency.py` still proves two blocking provider streams complete concurrently rather than serially.

## 9. Testing, told honestly

Run directly against this tree: `pytest -q` reports **244 passed, 13 skipped, 0 failed**. The pre-change baseline was 239 passing cases; five streaming-boundary and tool-exception cases were added. `CLAUDE.md` now carries the current count, while ADR-006 retains its historical 219 statement and appends a dated current-verification value. `scripts/check_doc_numbers.py` reruns pytest, ingest, and deterministic evals and rejects mismatched current summary claims in CI.

The 13 pytest skips are not failures; `tests/conftest.py` documents why some tests are environment-sensitive (it redirects `CUSTOS_DATA_DIR` to a throwaway temp directory at import time, before any test module loads, specifically so the rate limiter's persisted counters never touch the repo's real `data/counters.json` during a test run) and individual test modules skip cases that need a real vector store connection the pytest environment does not provide. No test in the suite calls a real Anthropic or Bedrock API; `tests/test_api.py`'s chat-endpoint tests patch `api_module._get_llm` directly (`unittest.mock.patch.object`), and nothing in the suite reads `ANTHROPIC_API_KEY`.

Evals are a separate, adversarial layer from pytest, one file per threat area in `evals/suites/`, run via `python -m evals.harness`. Run against this tree with Qdrant up and the demo corpus indexed (63 chunks across 9 documents, confirmed by the ingest command's own output): **Proven: 61, Skipped: 12, Failed: 0**, matching ADR-006's own reported figures exactly. The 12 skips are all LLM-dependent cases gated behind `--llm` and a real API key (`make evals-full`); `.github/workflows/ci.yml`'s `backend` job runs the 61 deterministic cases on every push and PR, with no `ANTHROPIC_API_KEY` anywhere in that job, across a three-leg matrix (`{qdrant, native}`, `{pgvector, native}`, `{qdrant, langgraph}`; the fourth combination, `{pgvector, langgraph}`, is a named, accepted gap in the matrix, not an oversight, per the workflow file's own comment). Without a running Qdrant, the same command still exits 0 (verified directly) but reports `Proven: 45, Skipped: 3, Not implemented: 1, Overall: NOT PROVEN`, because the two suites that need a real vector store (retrieval grounding and the T5 access-control hard gate) cannot run at all rather than failing. The harness prints a clean `NOT IMPLEMENTED` line and a `Vector store backend not available; skipping real path test` reason with no traceback; `CLAUDE.md` now describes that exact behavior.

The previously published 55-eval headline did not match any executable configuration and is now 61 with the exact Qdrant/ingest/harness command. The injection suite emits 13 results with Qdrant available: 7 structural, 3 seeded-detector, 2 full-corpus precision/recall, and 1 real retrieval-path case. The former 11/12 disagreement is corrected to that executable count. The count gate was negatively proven by changing the pytest claim from 244 to 245: it exited 1 naming `CLAUDE.md:15`, the stated value, and the real value before the deliberate edit was restored.

## 10. Two deploy paths, genuinely different

The live demo (`custos.andrewbolaji.com`) and any AWS customer deployment are not the same infrastructure, and the repo documents both without conflating them. `docs/DEPLOY_RUNBOOK.md` describes a single Hetzner CX22 VM running `docker-compose.prod.yml` (an `api` container plus a `qdrant` sidecar, bound to `127.0.0.1:8000` only), with Caddy in front auto-provisioning TLS via Let's Encrypt, and the React UI built separately and uploaded to Cloudflare Pages. That runbook contains an operational warning worth surfacing here because it is easy to silently break: the API's DNS record must stay DNS-only in Cloudflare (grey cloud), not proxied, because proxying would replace every visitor's real IP with a Cloudflare edge IP at the TCP layer, which would silently make the per-IP rate limiter (`src/custos/rate_limiter.py`, keyed on `CUSTOS_TRUST_PROXY`-trusted `X-Forwarded-For`) treat all visitors as a handful of IPs and stop limiting anything, without erroring.

`deploy/terraform/` is the separate AWS path. Client transport now defaults to HTTPS and a missing ACM certificate refuses the plan; plaintext requires two explicit demo-only variables. The ECS service is mechanically limited to zero or one task because confirmations and every abuse/budget counter are task-local. The task definition has no persistent application-data mount. `deploy/EVIDENCE.md` records one dated Anthropic/egress/plaintext apply and teardown; it does not prove the current TLS default, Bedrock, or air-gapped configurations against a real account.

CI validates Terraform formatting and schema and runs five mocked plan tests covering certificate-present TLS, missing-certificate refusal, plaintext acknowledgement refusal/acceptance, and multi-task refusal. Mocking does not prove a live AWS apply or the account-id guard against real credentials. No CI job applies the backend Terraform; the deployment job publishes only the Cloudflare Pages frontend.

## 11. Operations

`src/custos/boot.py :: ensure_index_ready` compares the vector store's actual chunk count against a count computed fresh from the corpus manifest at boot (`compute_expected_chunks`), and reindexes on any mismatch, not only when the store is empty. `GET /api/health` is a readiness check, not a liveness check, per `docs/DEPLOY_RUNBOOK.md`'s own explicit warning: once a process has reported healthy once, nothing in the request path resets that state, so a Qdrant outage that happens after a successful boot does not flip `/api/health` back to degraded; it instead shows up as `/api/chat` and `/api/chat/stream` returning 503 per request. The runbook tells an operator to watch `/api/admin/status`'s `qdrant_connected` field or chat-endpoint error rate for that specific failure mode, not the health check. A concurrent-boot race is handled explicitly: `src/custos/api.py`'s `_self_heal_lock` ensures that if two load-balancer health probes land at nearly the same moment while the index is not ready, only one triggers a reindex; `tests/test_boot_readiness.py :: TestHealthSelfHeal.test_self_heal_lock_prevents_concurrent_reindex` verifies this by firing four concurrent health calls and asserting exactly one reindex attempt.

`src/custos/rate_limiter.py` tracks daily/monthly caps, per-IP rate, and per-session quota. The latter two are memory-only. Daily/monthly counters are file-backed and survive a process restart on a persistent VM, but not an ECS task replacement because the task has no application-data mount. All counters are task-local, so multiple tasks would multiply the nominal monthly cap; Terraform refuses that topology until shared state exists. Cost remains an estimate from fixed token assumptions, not metered billing data.

## 12. Known gaps and deliberate deferrals

| Gap | Conscious or oversight | Trigger to fix, if conscious |
|---|---|---|
| No real authentication on `/api/chat`, `/api/chat/stream`, `/api/ingest`; permissions are client-declared | Conscious, named explicitly in `THREAT_MODEL.md` and the `api.py` module docstring | Customer identity provider integration scoped and built (named as a live open question in `deploy/PREREQUISITES.md`) |
| Tier 2 PII (DOB, salary, address, personal names) not masked | Conscious, ADR-005 states the reason: naive regex on these types would corrupt legitimate operational answers | NER/disambiguation approach built and evaluated, not before |
| Both fully air-gapped Terraform configurations (`enable_egress=false`) are blocked at plan time by the Qdrant sidecar's Docker Hub dependency | Conscious, named directly in `deploy/PREREQUISITES.md` as a real, unresolved gap, not hidden | Sidecar image mirrored into the customer's own ECR |
| `/api/chat` (sync) can emit a confirmation event but never creates a real `PendingAction`, only `/api/chat/stream` can | Conscious per ADR-006, described as a pre-existing asymmetry deliberately replicated rather than fixed during an unrelated runtime comparison | None on record |
| Conversation history is client-supplied and could be forged to prime the model | Conscious, `THREAT_MODEL.md` states per-turn controls (gating, retrieval filtering, redaction) hold regardless of history content, and names server-side session storage as a future-phase item | Authenticated sessions built |
| Pending actions, abuse limits, and budget caps are task-local; ECS application state is ephemeral | Conscious for a one-task demo and mechanically enforced with `desired_count <= 1` | Multi-instance deployment becomes a requirement |
| Plain HTTP remains an explicit two-variable demo option | Conscious for isolated synthetic-data demonstrations; TLS is the default | Before any deployment holding real customer documents |

## 13. Where I most want your eyes

Whether the client-declared `user_permissions` model (section 6) is acceptable for however long it takes to wire in a real identity provider, given that it is the single control everything else in section 5 is layered on top of, `src/custos/retriever.py` and `src/custos/api.py`'s `_build_registry` show exactly how far that trust extends today. Whether the Bedrock deployment path and the air-gapped guard in `deploy/terraform/guard.tf` have actually been exercised against a real AWS account the way the Anthropic-direct path was in `deploy/EVIDENCE.md`, since nothing in the repo evidences that they have.
